Домашнее задание по теме «Инцидент-менеджмент»: постмортем реального сбоя GitHub, произошедшего 21–22 октября 2018 года.

---

## Постмортем: Деградация сервисов GitHub 21–22 октября 2018 г.

### 1. Сводка (Summary)
21 октября 2018 года в 22:52 UTC в результате плановых работ по замене неисправного оптического оборудования произошел разрыв сетевой связности между сетевым концентратором и основным дата-центром на Восточном побережье США. Несмотря на то, что связь была восстановлена всего через **43 секунды**, этот кратковременный сбой запустил цепочку событий, которые привели к **деградации сервиса на 24 часа и 11 минут**.

В течение этого времени пользователи могли наблюдать устаревшую или противоречивую информацию на сайте, не работать могли Issues, Pull Requests, а также были приостановлены вебхуки и сборка GitHub Pages. Данные в Git-репозиториях не пострадали, однако для нескольких секунд записей в базу данных потребовалась ручная сверка.

### 2. Влияние (Impact)
Инцидент затронул несколько внутренних систем GitHub, что привело к следующим последствиям для пользователей:

- **Отображение устаревшей и несогласованной информации**: данные, хранящиеся в MySQL (метаданные Issue, PR и т.д.), могли отображаться некорректно из-за отставания реплик чтения.
- **Недоступность функциональности**: на протяжении большей части инцидента GitHub не мог обслуживать вебхуки и создавать/публиковать сайты GitHub Pages.
- **Потенциальная потеря данных**: хотя в итоге данные не были потеряны, существовала угроза потери нескольких секунд записей, которые не успели реплицироваться до сбоя. Для их сверки потребовалась ручная работа.
- **Длительность**: общая деградация сервиса составила 24 часа 11 минут.

### 3. Хронология (Timeline)
Ниже приведена ключевая хронология событий (время указано в UTC):

- **21 октября, 22:52**: Плановые работы по замене оптического оборудования приводят к разрыву связи между Восточным побережьем и основным дата-центром. Связь восстанавливается через 43 секунды. Однако за это время **Orchestrator** (система управления топологией MySQL на основе Raft) теряет кворум и инициирует аварийное переключение (failover) кластеров на Западное побережье.
- **21 октября, 22:54**: Системы мониторинга начинают генерировать оповещения о многочисленных сбоях.
- **21 октября, 23:02**: Дежурные инженеры обнаруживают, что топология кластеров БД находится в неожиданном состоянии — репликация настроена только на Западное побережье.
- **21 октября, 23:07–23:11**: Инженеры блокируют инструменты развертывания, чтобы предотвратить дальнейшие изменения. Статус сайта переводится в «желтый», затем в «красный», подключается координатор инцидента.
- **21 октября, 23:13**: К работе привлекаются инженеры по базам данных. Становится ясно, что проблема затрагивает несколько кластеров. Принимается решение о **приоритете целостности данных над скоростью восстановления**: приложение продолжает работать в деградированном режиме, чтобы не потерять данные, записанные на Западном побережье.
- **21 октября, 23:19**: Для снижения риска потери данных приостанавливается доставка вебхуков и сборка GitHub Pages.
- **22 октября, 00:41**: Начинается процесс восстановления кластеров из резервных копий.
- **22 октября, 06:51**: Некоторые кластеры восстановлены, начинается репликация с Западного побережья. Однако из-за возросшей нагрузки репликация отстает, и пользователи видят несогласованные данные.
- **22 октября, 11:12**: Все первичные серверы БД снова развернуты на Восточном побережье, но реплики чтения сильно отстают.
- **22 октября, 16:24**: После синхронизации реплик выполняется обратное переключение на исходную топологию. Статус остается «красным» до полной обработки накопившейся очереди данных.
- **22 октября, 16:45**: Начинается обработка накопившихся вебхуков (более 5 миллионов) и сборок Pages (80 тысяч).
- **22 октября, 23:03**: Вся очередь обработана, целостность систем подтверждена, статус переведен в «зеленый».

### 4. Первопричина (Root Cause)
Первопричиной инцидента стал **кратковременный разрыв сетевой связности**, вызванный плановыми работами. Этот разрыв привел к тому, что система **Orchestrator**, отвечающая за автоматическое переключение при отказе (failover), повела себя в соответствии с заложенной в нее логикой, но эта логика не была рассчитана на подобный сценарий.

Orchestrator, используя алгоритм консенсуса Raft, потерял связь с первичным дата-центром и, получив кворум с другими узлами, инициировал переключение записи на Западное побережье. Когда связь восстановилась, приложения начали писать данные в новый первичный кластер на Западе. В то же время на Восточном побережье остались записи, которые не успели реплицироваться. Возникла ситуация **«двух первичных узлов» (split-brain)**, когда в обоих дата-центрах были данные, отсутствующие в другом. Это сделало невозможным безопасное обратное переключение без риска потери данных.

Ключевым фактором стало то, что конфигурация Orchestrator допускала автоматическое переключение между регионами, хотя приложения не были рассчитаны на работу с межконтинентальной задержкой при записи. Как отметил сам GitHub, «Orchestrator действовал в соответствии с конфигурацией, несмотря на то, что наш прикладной уровень не мог поддерживать такое изменение топологии».

### 5. Устранение (Resolution)
Восстановление было сложным и многоэтапным, так как приоритет отдавался **целостности данных**, а не скорости.

1.  **Приоритизация данных**: Инженеры приняли сознательное решение не выполнять обратное переключение, которое могло привести к потере данных, и вместо этого приостановили работу сервисов, создающих новую нагрузку на запись (вебхуки, Pages).
2.  **Восстановление из резервных копий**: Была запущена процедура восстановления кластеров MySQL из резервных копий, хранящихся в облачном хранилище. Это был длительный процесс, так как ранее GitHub не приходилось восстанавливать целые кластеры таким образом.
3.  **Синхронизация и переключение**: После восстановления кластеров на Восточном побережье была настроена репликация с Западного побережья. После того как реплики догнали первичные узлы, был выполнен контролируемый обратный переход (failover) на исходную топологию.
4.  **Обработка очереди**: Только после стабилизации топологии и подтверждения целостности данных началась обработка накопившейся очереди вебхуков и сборок Pages.

### 6. Извлеченные уроки (Lessons Learned)
Инцидент выявил несколько важных уроков:

- **Опасность автоматизации без учета прикладных ограничений**: Автоматические системы (Orchestrator) могут принимать решения, которые технически корректны, но катастрофичны для приложений, не рассчитанных на такие условия (например, на высокую межрегиональную задержку).
- **Недостаточная коммуникация**: Первоначальные оценки времени восстановления были неточными, так как не учитывали всех факторов (например, нелинейный рост нагрузки). GitHub признал это и обязался улучшить коммуникацию.
- **Ограниченность статус-страницы**: Использование только трех статусов (зеленый/желтый/красный) не давало пользователям понимания, какие именно компоненты платформы затронуты.
- **Необходимость активного тестирования отказоустойчивости**: Инцидент показал, что пассивных мер (резервирования) недостаточно; требуется активное моделирование сбоев (chaos engineering).

### 7. Корректирующие действия (Action Items)
По итогам анализа GitHub анонсировал ряд технических и организационных мер:

- **Настройка Orchestrator**: Изменить конфигурацию, чтобы **предотвратить автоматическое повышение первичных БД до статуса «мастер» за пределами региона**. Это должно предотвратить подобные сценарии в будущем.
- **Улучшение статус-страницы**: Перейти на новую систему статусов, которая будет отображать состояние **отдельных компонентов платформы**, а не только общий статус.
- **Переход к архитектуре Active/Active/Active**: Ускорить работу над проектом, целью которого является **обслуживание трафика GitHub из нескольких дата-центров** с поддержкой резервирования N+1 на уровне объекта. Это позволит выдерживать полный отказ одного дата-центра без влияния на пользователей.
- **Внедрение Chaos Engineering**: Начать систематическую практику **валидации сценариев отказа** до того, как они повлияют на пользователей, с инвестициями в инструменты для внедрения сбоев (fault injection).

### Заключение
Инцидент 21 октября 2018 года стал важным уроком для GitHub. Он продемонстрировал, что даже при наличии многоуровневой избыточности сложные взаимосвязи между автоматизацией, конфигурацией и прикладной логикой могут привести к масштабным и длительным сбоям. Выбор в пользу **целостности данных** в ущерб скорости восстановления был правильным с точки зрения долгосрочного доверия пользователей, но сам инцидент ускорил внедрение более надежных архитектурных и организационных практик.
